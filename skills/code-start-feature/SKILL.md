# code-start-feature：新功能规划与实现

帮开发者**从 0 到 1 规划并实现一个全新功能或独立能力片段**。  
核心基调：**轻量规划、5点一线雷达粗扫、严守规范红线、确认后再动代码、单轨彻底实现、拒绝过程冗余与 Token 浪费**。

---

## ⚡ 阻断级规范红线（动代码前必查，违规直接打回）

写代码前必须严格对照，严禁擅自偏离：

1. **实体主键防 JS 精度丢失**：库表自增 `id`（BIGINT）或大整数主键，对应后端向前端输出的实体字段**必须用 `String`** 接收输出（防前端 JS Number 精度丢失）；业务主键统一用 `*_code`。
2. **权限标识严格字面量**：接口权限标识与路由直接写三段式字面量（如 `@SaCheckPermission("system:user:add")` 或权限守卫字面量），**严禁**拆成碎常量类；公开/免登接口如实标注。
3. **团队分工与前后端对齐纪律**：
   - 前端大块业务逻辑由前端专人负责，严禁后端 Agent 擅自大面积重写前端业务；
   - 但对于**字段名微调、大小写修正、枚举值更正、参数定义对齐等局部轻量改动**，**经用户确认后可以直接改动前端代码**，一步到位对齐，严禁在后端强行堆砌兼容胶水层。
4. **单轨彻底改造，严禁擅自双轨制**：
   - 改造即替换，原接口或旧逻辑直接更正或废弃；**严禁**自作聪明搞双轨制（新旧两套接口并存、兼容门面兜底、以及层层 if-else 参数兼容）；
   - **除非用户明确指示“需要做双轨”，否则一律单轨彻底替换改造**！
5. **依赖注入防形式主义**：注解注入（`@Autowired`/`@Resource`）与构造器注入均合法，**绝对禁止**擅自批量把注解注入改成构造注入。
6. **工具类使用纪律**：框架已有 → 成熟三方库（如 Hutool/Guava） → 再新建；**零调用不误删**；更名必须全仓替换，**禁止**保留旧名 `@Deprecated` 转发。
7. **注释规范**：类头 `@author` 必须写真人名（**严禁写 bot、AI、项目假名**）；注释只写已确认事实与原因，**严禁写 TODO、未来规划、争议选项或完成度**。
8. **跨模块/跨服务共享**：直用公共 Bean，严禁在消费端私建空壳本地 Bean，严禁无意义的缓存转换拷贝。
9. **严防敏感配置**：严禁硬编码密码、密钥，严禁改动或提交本地私密环境变量（如 `.env` 实值）。

## 📋 功能规划轻重分级（拒绝动辄几千字长表格烧 Token）

严禁在规划阶段大段堆砌长篇散文和复杂表格，按需求分级：

### 1. 简单小功能（3～5 句话极简施工卡）
对单页面/单一接口的新增，只需用几句话说明：
- **谁在哪操作**：哪个页面、什么角色；
- **调什么接口**：URL、HTTP 方法、权限字面量；
- **改了什么数据**：存哪张表、入参核心字段。

### 2. 复杂跨端/多状态功能（精简四件套契约）
仅当涉及多端流转、复杂状态机的业务时，才输出轻量级中和契约卡（核心业务动线、涉及界面、入出参动作契约、业务防呆规则闭环）。

## 🚀 执行流程（三步走）

### 1）前置全系统粗调研、文码核验与对齐
- **5 点一线雷达粗扫**：动代码前花 30 秒快速扫描：
  1. **前端入口点**：搜前端代码，定位哪个组件调用的 API、传什么参数格式、出参取什么字段；
  2. **网关/路由点**：核查路由前缀与转发映射是否匹配；
  3. **后端控制点**：定位 Controller/Handler（看真实权限码、入参 Bean 定义）；
  4. **数据与缓存点**：看 Service 关键分支（看有无涉及共享缓存、跨服务调用、库表字段）；
  5. **基线文档点**：查阅现有设计文档或说明书中对该功能的原始约定。
  **严禁闭门造车重复造轮子**，看有无可复用的公共组件/枚举/工具类。
- **文码冲突智能推断与探讨**：
  若发现【代码实码】与【设计文档】存在出入，**严禁盲从代码，也严禁死板偏信文档**，必须抓证据链智能推断：
  - 若前端真实调用已正常跑通、或代码提交时间明显更新 ➔ **推断代码是对的，文档滞后了**；
  - 若代码逻辑违背了全局规范（如搞了双轨制、实体 id 误用 Long、私建空壳 Bean） ➔ **推断代码写歪了，文档才是正确意图**。
  **互动探讨三步法（3 段话请用户拍板）**：
  1. 说明冲突点（代码怎么写的 vs 文档怎么写的）；
  2. 说明智能推断结论与依据（我推断 X 是对的，因为……）；
  3. 给出清晰选项（A. 按代码走，顺带更文档 / B. 按文档走，重构代码），**用户拍板后再动工**。
- **轻量施工卡与列文件**：按分级给出施工卡，列出要新建/修改的文件路径清单（新建标「新建」，修改标「改」）；动库表/对外路径/权限码等契约先请用户确认。

### 2）用户确认后再动代码
- 用户说「确认 / 行 / 开始」后动手，按实体 ➔ 数据层 ➔ 业务层 ➔ 接口层 顺序推进。
- **单轨彻底改造**：直接落实新逻辑，不建临时兼容垫片。
- **顺手微调**：同文件内发现的明显笔误可直接顺手修；严禁跨文件跨模块蔓延。

### 3）自检与收尾
- 本地执行最短验证（如模块编译或语法检查）；
- **去除过程版本控制干扰**：
  - 平时不用执行 `git status` / `svn status`，不输出版本控制长日志；
  - 仅在收尾时：有新增文件统一跟踪（`git add` / `svn add`），改名使用重命名（`git mv` / `svn move`），删除使用删除指令（`git rm` / `svn delete`）；
- 汇报：1～3 句人话说清改了什么、怎么验证，末尾问一句「需要生成提交说明吗？」（用户明确要才给一行，不要不给）；
- **文档防注水**：只有真正产生新模块、新端口或架构变动时才同步文档（严格限 1 行表格或 1～2 句事实），**严禁把任务实现细节、排查总结写进正式文档**。
