# code-refine-feature：局部完善与修补功能

针对**已有页面、已有接口或已有业务链路**进行**局部完善、缺陷修补、前后端接口适配与流程闭环**。  
核心基调：**快修直达、严守单轨改造（拒绝双轨屎山与胶水层）、前后端精准对齐、拒绝过程冗余与 Token 浪费**。

---

## ⚡ 阻断级规范红线（动代码前必查，违规直接打回）

改代码前必须逐条对照，严禁擅自偏离：

1. **实体主键防 JS 精度丢失**：库表自增 `id`（BIGINT）或大整数主键，对应后端面向前端传输的实体字段**必须用 `String`** 接收输出，防前端 JS 精度丢失；业务主键用 `*_code`。
2. **权限标识严格字面量**：接口权限与路由直接写清晰的字面量（如 `@SaCheckPermission("auth:user:update")`），**严禁**拆成碎常量类；公开或仅需登录的端点如实标注，严禁造假。
3. **团队分工与前后端对齐纪律**：
   - 前端大块业务逻辑由专门前端同事负责，**严禁后端 Agent 越俎代庖擅自重构大块前端逻辑**；
   - 但对于**字段名微调、大小写修正、枚举值更正、参数定义对齐等局部轻量改动**，**经用户确认后可以直接改动前端代码**！一步到位对齐，绝不让后端硬背无谓的胶水负担。
4. **单轨彻底改造，严禁擅自双轨制**：
   - 既然要改造，说明原有功能/接口有问题，重定义是必然的。**原旧接口/错误代码直接更正或废弃**；
   - **严禁**自作聪明搞双轨制（如新老两套接口并存、在 Controller/Service 堆砌新老参数兼容 if-else、搞无谓的“兼容门面兜底”）；
   - **除非用户明确指示“需要做双轨”，否则一律单轨彻底替换改造**！
5. **依赖注入防形式主义**：字段注解注入（`@Autowired`/`@Resource`）与构造器注入均合法，**绝对禁止**擅自批量把注解注入改成构造注入。
6. **工具类使用纪律**：框架已有 → 成熟三方库（如 Hutool/Guava） → 再新建；**零调用不误删**；更名必须全仓替换，**禁止**保留旧名 `@Deprecated` 转发。
7. **注释规范**：类头 `@author` 必须写真人名（**严禁写 bot、AI、项目假名**）；注释只写已确认事实与原因，**严禁写 TODO、未来规划、争议选项或完成度**。
8. **跨服务/跨模块共享**：直用公共共享 Bean，**严禁**在消费端建本地空壳 Bean，**严禁**无意义的缓存转换拷贝。
9. **严防敏感配置**：严禁硬编码密码、密钥，严禁改动或提交本地私密环境变量（如 `.env` 实值）。

## 🚀 极简两级执行通道（拒绝死锁拖沓）

根据改动性质自动走对应通道，不再一刀切傻等确认：

### 通道 A：快修直达（日常小修补 / 内部实现 / Bug 修复 / 参数防呆）
- **判定标准**：**不改动对外契约**（不改库表字段、不改现有 HTTP 路径、不改外部已在用的 JSON 字段名、不改已有权限码）。
- **执行方式**：
  1. 快速排查代码，定位根因；
  2. 手术刀式直接改好代码；
  3. 执行最短编译/语法自检；
  4. 给出大白话汇报（改了哪里、怎么验证）。无需分成两轮回合反复拉扯。

### 通道 B：契约门禁（涉及库表 / HTTP路径 / JSON字段名 / 权限码变动）
- **判定标准**：改动会破坏对外兼容性、或者需要在多种方案中二选一。
- **执行方式**：
  1. 停下来用 2～3 句白话说明现状与分歧；
  2. 给出 2～3 个清晰选项并给出推荐；
  3. **用户拍板确认后，再动手改代码**。

## 🌐 任务前置：5 点一线雷达粗扫与文码冲突智能推断（严禁管中窥豹）

在动任何代码前，严禁“只看单个文件”或“只信文档”。必须花 30 秒执行端到端全链路粗扫：

### 1. 5 点一线「雷达粗扫」（只查签名/路径，不精读全代码，防 Token 浪费）
1. **前端入口点**：搜前端代码，定位哪个组件调用的 API、传什么参数格式、出参取什么字段；
2. **路由网关点**：核查路由前缀（确认去前缀与微服务/模块映射是否匹配）；
3. **后端控制点**：定位 Controller/Handler（看真实权限码、入参 Bean 定义）；
4. **数据与缓存点**：看 Service 关键分支（看有无涉及共享缓存、跨模块调用、库表字段）；
5. **基线文档点**：查阅现有设计文档中对该功能的原始契约约定。

### 2. 文码冲突智能推断与互动探讨（代码与文档不一致时）
若发现【实码链路】与【基线文档】存在差异，**严禁盲从代码，也严禁死板偏信文档**，必须抓证据链智能推断：
- **推断依据**：
  - 若前端真实调用已正常跑通、或代码提交时间明显更新 ➔ **推断代码是对的，文档滞后了**；
  - 若代码逻辑违背了全局规范（如搞了双轨制、实体 id 误用 Long、私建空壳 Bean） ➔ **推断代码写歪了，文档才是正确意图**。
- **互动探讨三步法（3 段话请用户拍板）**：
  1. 说明冲突点（代码怎么写的 vs 文档怎么写的）；
  2. 说明智能推断结论与依据（我推断 X 是对的，因为……）；
  3. 给出清晰选项（A. 按代码走，顺带更文档 / B. 按文档走，重构代码），**用户拍板后再动工**。

### 3. 精准单轨对齐（拒绝双轨制）
- 搞清全景链路后，**只精读真正要修改的 1～2 个核心类的方法实现**，精准动手术；
- 若前端已有调用合理：后端按单轨承接，废弃老接口/老逻辑；
- 若前端调用存在参数值有误、大小写混淆、字段拼写笔误等局部问题：**向用户说明并确认后，直接修改前端代码**，前后端一步到位对齐，**严禁**在后端堆砌怪异的双轨兼容门面！

## ✂️ 顺手做的清晰界限（告别教条垃圾堆）

- **允许且提倡**：在**当前正在修改的同一个文件内**，顺手看到的明显空指针隐患、语法拼写小笔误、未使用的局部变量，**直接顺手修掉**，并在汇报里一句话顺带说明即可。
- **严格禁止**：跨文件、跨模块去改无关的代码，严禁借机搞大面积格式化或风格重构。

---

## 🚫 彻底去除版本控制过程冗余与 Token 浪费

- **严禁在开发过程中频繁执行 `status`**，严禁在对话中输出无意义的长篇版本控制状态日志！
- **日常修改**：普通文件的修改由版本控制系统自动跟踪，**开发过程完全不需要执行任何状态命令**！
- **仅在收尾最后一步**：
  - 若**新建了文件**，运行一次添加（Git: `git add <file>` / SVN: `svn add <file>`）；
  - 若**重命名了文件**，必须使用重命名（Git: `git mv` / SVN: `svn move`）；
  - 若**删除了版本库文件**，使用删除（Git: `git rm` / SVN: `svn delete`）；
  - **若没有新增/删除/改名文件，直接跳过版本控制操作，完全不在汇报里提**！

## 📝 极简大白话收尾汇报（3 段话，拒绝八股文）

完成代码修改与自检后，直接用 3 段日常中文汇报，拒绝机械填空：

1. **改了什么**：1～3 句话说明在哪个文件改了什么、解决了什么问题。
2. **怎么验证**：提供最短验证方式（如模块编译命令，或说明前端点哪测试）。
3. **提交提示**：
   - 结尾自然附一句「需要生成提交说明吗？」（用户明确要才给一行 `提交说明：<说明>`，不要不给）。

## 🎯 边界与近邻排除（Near-Neighbor Exclusions）

- **不承接从 0 到 1 的全新业务能力开发**：新建全套独立功能/大模块 ➔ 引导至 `/code-start-feature`；
- **不承接全局规范重构与架构体检**：全仓健康度扫描、规范治理、文档脱水 ➔ 引导至 `/code-repo-steward`；
- **严禁借机擅自重构无关代码**：本技能只聚焦目标缺陷或接口适配的靶向手术，严禁越界大动干戈。

---

## 📦 输入与输出契约（Input & Output Contract）

- **输入契约**：
  - 用户指出具体接口 404、前后端联调不通、参数漏传、字段大小写不一致或局部逻辑缺陷；
  - 自动走两级通道分流：不改契约的走通道 A（快修直达），涉及契约变更的走通道 B（先给 2～3 个选项拍板）。
- **输出契约**：
  - **通道 A 产出**：靶向修改后的核心代码 + 最短编译验证 + 3 句话大白话汇报；
  - **通道 B 产出**：分歧与选项分析 ➔ 用户拍板后产出干净代码与汇报。

---

## 🛡️ 安全与回退边界（Rollback Boundary）

- **前后端协同防空转**：前端轻量参数改动必须经用户确认后一步到位对齐，严禁在后端堆砌兼容胶水代码；
- **自包含自检**：每次修补必须保证当前服务/模块能独立通过本地编译；
- **绝不擅自执行 Commit**：只修改工作副本，提交权利属于开发者本人。
